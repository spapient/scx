# RFC：服务化 / 多租户设计（设计稿，未实现）

> 状态：**设计 only，不实现**。本文回答"scx 若要作为服务供多人/多项目使用，如何
> 在保持确定性内核与零第三方 crate 的前提下做进程内多库隔离、MCP 鉴权与记忆库
> 沙箱"。实现与否、何时实现由用户决定；任何实现都必须先更新本 RFC 为"已实现"。
> 日期：2026-10-25，基线版本 0.5.0。

## 0. 约束声明（不可违反）

1. **确定性核心不变**：压缩内核（`scx::compress`）是纯函数、无随机源、无网络；
   多租户只发生在**记忆库与接入层**，绝不把 query/输入路由到内核之外。
2. **零第三方 crate 铁律**：服务化/鉴权若实现，仍用 std 手写（本轮设计不含任何
   新依赖；若未来引入，必须走用户显式批准的 feature-gate 并重新评估确定性承诺）。
3. **只删不改 / 证据地板**：任何租户侧策略（配额、裁剪）不得导致证据行静默丢失；
   与 `--max-tokens` 相同的"证据地板最高优先"语义。
4. **本地优先**：设计默认仍是本地进程；服务化是可选包装，不是默认部署形态。

## 1. 进程内多库隔离（--mem-dir 多实例）

现状：记忆库是本地目录，`--mem-dir` 已支持任意路径；多进程共享同一目录已有
`acquire_all` 固定锁序契约（`docs/locking.md`）。多租户的进程内形态 = **一进程
多库句柄**。

### 设计

- 引入 `scx::memory::Handle`：封装 `(mem_dir, config 快照)`，`Handle::open(dir)` /
  `Handle::open_read_only(dir)`；**不新增全局状态**——现有函数保持 `dir: &str`
  参数签名（避免破坏零依赖纯函数承诺），Handle 只是参数打包。
- 隔离边界：**目录即租户**。每个租户一个 `mem-dir`；case id 天然带日期前缀，
  目录隔离即 id 空间隔离，无需改存储格式。
- 进程内并发：不同 Handle 的目录不同 → 无锁竞争；同一目录多 Handle = 当前
  多进程语义的进程内版，复用 `acquire_all`。
- MCP 层：`scx-mcp` 启动时可带 `--mem-dir`；多租户形态为**每租户一个 server
  进程**（进程隔离最强），进程内多 Handle 仅用于库间迁移/对比工具。

### 不做

- 不引入数据库/嵌入式 KV；不缓存整库于内存（10k case 冷启动 ~1s 已在性能预算内）。

## 2. MCP 多租户鉴权（API key / token 设计）

现状：`scx-mcp` 是 stdio JSON-RPC，本机进程通信无鉴权需求（P2 已交付）。

### 设计（若未来做远程 MCP/HTTP 桥）

- **最小形态（推荐）**：保持 stdio + 本机权限边界。多租户 = 每租户独立进程 +
  独立 `--mem-dir` + 独立 `--policy-file`；鉴权退化为 OS 用户隔离（Unix 权限）。
- **远程形态（需用户明确立项）**：
  - 传输：streamable HTTP 之上封装 scx-mcp（复用 `src/json.rs` parser，零依赖）。
  - 凭证：`X-SCX-Tenant` + `X-SCX-Key` 头；key 为租户级随机 32 字节 hex
    （生成用 `std::env` 随机源**不可用**——确定性红线禁止随机源进内核；key
    生成必须由**外部工具/管理员**预置到租户配置文件，服务只做常量时间比较
    （`subtle` 无依赖版：逐字节 XOR 累加比较，避免早期返回）。
  - 令牌表：租户配置文件（TOML 子集，复用 `conf::parse`）`{tenant, key_sha256,
    mem_dir, policy_file, quota}`；服务只存 **key 的 SHA256**（手写 SHA-256 已存在
    `semantic` 中，可提取到公共模块），不存明文。
  - 作用域：key 只授权 `compress_context` / `recall`；**拒绝** `--store` 写权限
    可单独开关（租户配置文件 `allow_store = false`）。
- 审计：每次工具调用写一行审计（tenant/工具/时间/字节数）到租户目录
  `.scx-audit.log`；**不记录输入正文**（避免把敏感 payload 落盘成审计数据）。

### 不做

- 不做 OAuth/SSO/多因素；不做 key 轮换自动过期（留给运维层 cron）。

## 3. 记忆库沙箱（配额 / 隔离 / 脱敏边界）

### 配额

- 已有：`--max-bytes` 总容量软配额（P1 前既有，超限拒绝写入）。
- 补充设计：租户配置文件可叠加 `quota = { max_bytes, max_cases }`；写入前双重
  检查（目录字节数 + case 计数），超限报 `tenant-quota` 错误（与 `overflow` 家族
  同构：**明确报错，不静默**）。
- 逐租户审计：`bin/scx-eval stats` 扩展租户维度（本轮不实现）。

### 隔离

- 目录隔离 + 锁序隔离（不同目录零共享锁）；同一租户内并发写仍走 `acquire_all`。
- 索引/qmap/指纹缓存的 key 空间：**不得**跨租户共享（现实现缓存都在 mem-dir 内，
  天然隔离；若未来加全局缓存层，必须按 `mem-dir` 分片——写进实现约束）。

### 脱敏边界（现状 + 补强）

- 现状：入库前已知模式脱敏（password/token/Authorization/Bearer/URL 用户信息），
  **不是通用 DLP**（README 已声明）。
- 服务化后边界不变且更硬：**服务端不新增任何脱敏逻辑**——脱敏是**写入方责任**
  （`--store` 前由调用方完成），服务只做配额与审计。理由：通用 DLP 需要上下文
  理解，超出确定性内核承诺；误脱敏会破坏"只删不改"的原文可追溯性。
- 审计日志只记元数据（见 §2），不记 payload。

## 4. 保持确定性核心的约束

| 层 | 确定性 | 约束 |
|---|---|---|
| `scx::compress`（内核） | 必须 | 纯函数、无随机源、无网络、无 I/O；多租户不改此层 |
| `scx::memory` | 必须（确定性排序/召回） | key 生成、配额检查、审计均不得引入随机源；时间戳用外部传入的 `now_s`（现有签名已如此） |
| MCP 服务层 | 不承诺 | 进程编排/鉴权/审计属于运行时外壳；但**不得**把任何随机值传入内核或记忆库打分 |
| 密钥 | 外部预置 | 服务不生成 key；SHA256 比较用常量时间 |

实现约束备忘（若实现）：`semantic.rs` 的手写 SHA-256 提取为 `scx::sha256`
公共模块（feature-gate 外，std 实现），供令牌表校验复用；`conf::parse` 已可供
租户配置文件复用；无新依赖、无随机源、无网络。

## 5. 不做清单（本轮明确不做）

- 不实现 HTTP 服务器、key 管理、配额强制执行、审计写入——均为设计；
- 不改 `compress`/`memory` 现有公开签名（Handle 是未来可选的打包层）；
- 不新增第三方 crate；
- 不把"服务化"设为默认部署形态。
