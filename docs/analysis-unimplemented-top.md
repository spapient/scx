## 1. 逐项深度分析

### 1.1 P18-整合评测（组合矩阵）

**现状**：bench.py 已具备 cut 分档（<2%/2-10%/10-35%/>35%）与 manifest 冻结闭环；A2 fidelity 门禁按分档阈值断言。但 `--fold/--entropy/--auto-anchor/--cluster` 四新开关从未在冻结集上评测过——它们的正确性只有单测 + golden 默认关，**开启路径无端到端证据**。

**差距**：32 组合（2^5）全跑约 32×48 文件——成本可控（压缩是 ms 级），但结果必须能解释"每个信号独立贡献 + 叠加不互斥"。

**顶级方案（业界做法：消融矩阵 + 单调性门禁）**：
- 5 信号（semantic/fold/entropy/anchor/cluster）做**独立+成对**消融：只测 6 个关键配置（基线、5 个单开、+fold×entropy 组合），放弃全 2^5 笛卡尔——消融科学上只需要主效应 + 一个交互项。
- 门禁断言升级为**单调性**：任一单开配置 cut 不劣于基线（信号必须只增不减），fidelity 用既有 A2 分档断言守住。
- 产出 `config/bench/bench_p17_ablate.csv` 冻结进 manifest。

**收益**：每个开关从"默认关零影响"升级为"开启有证据的增益"，回答用户最初的追问「质量和性能达标吗」。
**风险**：个别信号在个别语料上可能 cut 持平（不是负）——门禁按"不劣于"而非"严格提升"设阈，避免误杀。
**工作量**：bench.py 加 `--ablate` 模式约 60 行；跑批约 10 分钟；冻结 1 次。

### 1.2 P18-SuperCompress 同预算对照

**现状**：官方 mean cut 64.1%（24/24 证据，用户已接受）——即官方 kept≈36%；scx 冻结实测 cut 在 28~40% 区间（按语料档）。

**差距**：两口径差异（官方自报 vs scx 冻结实测），且从未在**同一预算约束**下比。

**顶级方案**：
- 固定预算 = kept 35%（对齐官方 kept≈36%），用 `--trim-ratio` 档位（已有 P6c 扫描机制）把 scx 拉齐到 35% 预算。
- 在同一 35% kept 下比较**fidelity 而非 cut**：cut 对齐后谁保真高谁赢——这才是压缩器的真实赛道（SuperCompress 官方论文口径也是按预算比答案保持率）。
- 结果标注：`官方自报（SuperCompress v2, 24/24）vs scx 冻结实测（本地 judge, 同预算）`——口径分离，不虚构同场。
- 落点：`tools/bench.py` 加 `--budget 0.35` 模式（二分 trim-ratio 找档），产出对照表。

**收益**：把"竞品对比"从论文数字变成**同预算可复算对照**——这是求职/CNAS/Linux 基金会背书时最硬的证据。
**风险**：预算校准需二分搜索 5-8 次压缩/文件——成本可接受。
**工作量**：bench.py 加预算模式约 80 行。

### 1.3 P18-版本 bump 0.11.0

**现状**：Cargo.toml 0.10.0。历史惯例：版本唯一来源 `CARGO_PKG_VERSION`，bump 时同步 README/memory.md 引用 + Cargo.lock。

**方案**：照 P12-E 惯例：`chore(version): 0.10.0 → 0.11.0` + 四新 flag 文档同步 + plan.md 版本行。零风险。

### 1.4 P18-文档/门禁扩展

**现状**：check_bench.sh 覆盖 lib/semantic/golden/clippy/fmt/manifest/A2，但不含 P17 新开关的开启路径；README/SKILL 未列 `--fold/--entropy/--auto-anchor/--cluster`。

**方案**：check_bench.sh 加一段「新开关冒烟」：`--fold 1`、`--entropy 1`、`--auto-anchor 1`、`--cluster 1` 各在 golden 样例上跑一次压缩断言退出码 0 + 输出非空 + 与默认关输出 diff 非空（证明开关生效）；README/SKILL 补 4 行 flag 说明 + 各一行使用示例。

### 1.5 #51 unwrap→expect 语义化 + 大端 try_into

**现状（#50 审查结论）**：105 处 unwrap/expect、11 处 panic/unreachable，**逐点核验全为安全不变量**（chunks_exact 余数、digit 边界、index 守卫、自生成 ASCII、create_dir_all 必错等）——无 bug 级崩溃路径，但工程上未达顶级（panic 消息无上下文、unwrap 泛化）。

**顶级方案（Rust 工业级惯例）**：
- 三档改造：**不变量 expect**（带不变量描述的消息，如 `expect("chunks_exact(8): 权重文件字节数必须为 8 的倍数")`）→ **结果类型化**（仅外部 I/O 路径，用 `io::Result` 上抛而非 unwrap）→ **保持不变**（测试/示例/死路径不动的 unwrap 保留，避免无意义 churn）。
- 按文件优先级：`index.rs`/`cache.rs` 大端 `try_into().unwrap()` → 显式 `[u8; 8]` 数组拷贝（`copy_from_slice` + 直接 u64::from_be_bytes）——**去掉 8 次边界检查分支**，顺带是微性能优化。
- 门禁：改造后 cargo test 全绿 + clippy 0；diff 检查无行为变化（golden 零漂移天然覆盖）。

**收益**：panic 消息可诊断（生产事故时省定位时间）；热点路径少分支。
**风险**：churn 大（116 处）——用 git 分文件提交，每文件过 golden。
**工作量**：3-4 个提交，每提交 ~30 处。

### 1.6 P17-A 可逆模板折叠（最高优先级偏差修复）

**现状**：`--fold` 实现为「骨架行 + 标记行」（`scx-fold: {n-1} rows folded (diffs: ...)`）——**信息丢失，不可逆**，偏离原案「模板 + 参数表可逆重建 round-trip 100%」。

**这是 cut 率与保真的双短板**：日志/JSON 语料里同一模板几百行，现在折叠只留 1 行 + diff 摘要，展开时参数不可恢复。

**顶级方案（对齐原案，顺带对标 SuperCompress 的模板参数化）**：
- 折叠判定（fold.rs 已有骨架相似聚类）→ **参数抽取**：`{...}`/`"..."`/`数值` 段提取为参数位，行 → `(模板 id, 参数元组)`。
- 输出：1 行模板（参数位占位符）+ 1 行紧凑参数表（每参数定长 + 分隔符，如 `|` 流）。
- 可逆重建：render 输出**展开后的完整原文**（逐字节一致）——round-trip 100% 达成，与 golden 零漂移不冲突（默认关）。
- 参数流本身可再被 trim 池化/行内裁剪，cut 叠加。
- 门禁：新增 `--fold 1` round-trip 测试（折叠 → 重建 → 与原文逐行相等断言），对齐原案门禁「round-trip 还原率 100%」。

**收益**：日志/JSON 语料 cut +10~20%（原案预期），且保真从"摘要"变"无损展开"——**这是 P18 对照 SuperCompress 的胜负手**（官方模板参数化同样思路）。
**风险**：参数位识别需防误抽（中文字符串里的数字/引号）——用 fold.rs 现有 is_param 判定 + 引号配对守卫。
**工作量**：fold.rs 输出格式重构 + render.rs 展开逻辑，~200 行，1 个提交。

### 1.7 P17-F compress 侧权重联动

**现状**：feedback 词环只调记忆库召回权重；compress 打分表 `DEFAULT_SCORES`（policy.rs:100）静态。

**顶级方案（确定性闭环，不引入状态泄漏）**：
- 不直接改 DEFAULT_SCORES（会破坏确定性），而是加**显式覆盖通道**：`--score-adj <path>` 读 `key=value` 权重覆盖文件（JSON/TOML），仅显式传入生效。
- feedback 侧加 `scx rate --export-weights` 导出当前 word_w/参数为覆盖文件 → compress 侧消费。两个确定性机制之间的**显式管道**，无隐式全局状态。
- 默认关、默认路径逐字节一致。

**收益**：记忆库学到的东西能作用于压缩保留决策（"这个 token 用户总标 good → 多保留"），全链路可复现。
**风险**：scope 膨胀——P18 清单已大，此项降级为 P18 后续可选（plan.md 已如此标注）。

### 1.8 scores() 串行热点

**现状**：plan.rs :1098 串行打分，30MB 语料 20~30ms；P14 证明并行基建有效（dedup 并行 -36%）。

**顶级方案**：`scores()` 按 P14 `scan_fp` 模板并行化——每行打分独立（sumw/state/region/entropy 全是行局部），天然可并行；`std::thread::scope` + PAR_MIN 20k 分块，行数 < 阈值走串行（零开销小输入）。
**门禁**：bench_perf.py 对比 HEAD；大语料加速断言（如 ≥2MB 语料 ≤ 串行 60% 时间），小语料噪声内允许持平。
**收益**：30MB 档 20ms → 预期 <8ms；与 P14 的 dedup 优化形成完整并行管线。

### 1.9 MAX_DICT_WORD=16 bench 确认

**方案**：bench_perf.py 加一档 16 字节词表压力语料（含 approximately 等 13 字节词），断言与 8 字节旧档同数量级（<15% 回归）。纯验证，无代码改动。

## 2. 能力提强路径（超出现有清单的上限增量）

在 1.1-1.9 之上，以下方向把项目从「完成计划」推向「同预算赛道领先」：

### T1 全文级重复 token 池化（trim 池化推广，零依赖霍夫曼）
trim.rs 已有**行内** token 池化。推广到**全文级**：跨行高频 token（`ERROR`/`timeout`/路径片段）编码为短字典下标——zero-dep 确定性字典（按出现频次排序定下标，字典随压缩流前缀）。日志语料通常 30-50% token 是重复词——这是超越 SuperCompress 64.1% 的本地杠杆，且完全确定性、可逆（字典随流）。
- 落点：render.rs 输出字典 + 下标流；门禁 round-trip 100% + golden（默认关 `--dict 1`）。
- 与 1.6 可逆折叠正交：折叠消行、字典消 token，叠加 cut 可达日志语料 55-65%。

### T2 结构化保真压缩（JSON/日志键路径保持）
JSON 行保键路径、丢值细节（值替换为类型占位）——对 LLM 问答保真极高（键是语义锚）。确定性、可逆。与 1.6 模板参数化共享参数抽取基建。

### T3 熵编码尾段（fixed 预算下的最后 5-10% cut）
35% kept 预算内，trim 摘除的是「词」；尾部可以用**定长 token 截断 + 保序**（已有思路）或**行优先级截断**（plan 排序已有）——把它们做成预算驱动的自适应档位（`--budget 0.35` 自动调 trim-ratio + 截断），这正是 1.2 同预算对照需要的引擎。

### T4 工程顶级化
- #51 完成后引入 `cargo audit`-级自检（零依赖自制：`tools/audit_unwrap.py` 统计 expect 覆盖率，门禁 expect/panic 消息非空）。
- 性能 profile 进 CI：bench_perf.py 结果冻结阈值（P12-A 已建，扩到新档位）。
- 错误面收敛：唯一 panic 面 = `--weights` 文件解析（可诊断 expect）+ 内存目录权限（create_dir_all）。

## 5. 结论

- **未实现项没有「难」的，只有「没排期」的**：9 项全部在既有基建内可落地（评测闭环、并行基建、fold/trim 机制均已存在）。
- **能力提强的真实杠杆是 1.6 可逆折叠 + T1 全文字典**：把 cut 从 28-40% 推到日志语料 55-65% 区间，才能在同预算下与 SuperCompress 64.1% 正面可比——这不靠模型，靠确定性结构压缩，完全在红线内。
- 建议执行序：1.6 → 1.1+1.2（评测出证据）→ 1.5/1.8（工程+性能）→ 1.3/1.4（收尾 v0.11.0）→ T1 视评测结果决定。
