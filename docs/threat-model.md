# 威胁模型与安全论证

本文给出 `scx` 的威胁模型、信任边界、安全设计原则的应用，以及常见实现弱点的对抗措施。
对应 OpenSSF Best Practices silver 级的 `assurance_case` 与 `documentation_security` 条款。

## 1. 资产

| 资产 | 位置 | 影响若受损 |
| --- | --- | --- |
| 用户输入的日志、命令输出、diff | 进程内存、临时文件 | 泄漏可能暴露凭据、客户数据、内部拓扑 |
| 本地记忆库（case memory） | `--mem-dir`（默认 `~/.scx-memory`） | 泄漏历史排障上下文 |
| 脱敏后的输出 | stdout / 文件 / MCP 响应 | 被误当已净化数据二次分发 |
| 发布凭据 | 维护者本地 | 供应链投毒 |
| 发布资产 | crates.io / npm / Homebrew / GitHub Release | 供应链投毒 |

**不在资产范围**：用户的模型权重、第三方服务凭据、宿主机内核。

## 2. 信任边界

```
[不可信] 用户输入文本 ──────┐
[不可信] 文件路径与参数 ─────┤
[不可信] MCP 客户端请求 ─────┼──> [scx 进程] ──> [可信] 本地文件系统写入点
[不可信] 配置文件内容 ───────┘         │
                              [半可信] 原生 GPU 内核（仓内源码，无外部输入）
```

- **边界 A（输入文本）**：任意长度、任意编码、含控制字符、含伪造的分隔符。
- **边界 B（路径与参数）**：攻击者可控的 `--mem-dir`、`--store`、输出路径。
- **边界 C（MCP 客户端）**：客户端可能被提示注入操纵，传入恶意文本或超大负载。
- **边界 D（配置文件）**：`scx setup` 读写的第三方工具配置可能被预先投毒。
- **边界 E（构建与分发）**：源码到二进制的转换链路。

## 3. 威胁与缓解

### T1 恶意日志内容导致解析崩溃或资源耗尽

**威胁**：超长单行、深层嵌套括号、EB 级输入、刻意构造的正则灾难性回溯。

**缓解**：
- 仓内正则实现限制回溯与重复上限；不使用用户可控的模式构造回溯型表达式。
- 输入按行流式处理，内存按 `--max-mem` 分块控制。
- 所有解析入口返回 `Result`，错误向上冒泡为可读消息；生产路径裸 `unwrap` / `expect` / `panic` 为 0（由 `scx-tooling audit` 复核）。
- 全局 `forbid(unsafe_code)`，不存在越界读写类内存安全问题。

### T2 输出被误认为"已脱敏"

**威胁**：用户把 `--store` 的输出当作可直接分发的安全数据。

**缓解**：
- `SECURITY.md` 明确声明脱敏是**尽力而为的已知模式匹配**，不是通用 DLP。
- 脱敏失败或不确定时不静默通过，输出中保留原始行并给出可解释提示。

### T3 记忆库泄漏

**威胁**：`--mem-dir` 位于同步目录或权限过宽的路径，历史上下文外泄。

**缓解**：
- 文档要求按普通敏感数据管理 `--mem-dir` 的访问权限。
- 写入点限定在用户显式指定的目录，不写入全局共享位置。
- 不自动上传、不联网同步。

### T4 路径穿越与任意写入

**威胁**：通过文件名或记忆库键构造 `../` 逃逸到目标目录之外。

**缓解**：
- 所有落盘路径由受信前缀拼接并做规范化校验，拒绝逃逸结果。
- 记忆库键做白名单化处理，不接受包含分隔符的键。

### T5 `scx setup` 覆写他人配置

**威胁**：命令把 MCP 配置写入错误账户或错误路径，或覆盖掉用户原有 server 配置。

**缓解**：
- 写入前解析真实 home（不依赖被重定向的环境变量），跨平台路径单独测试。
- 写入前创建 `<配置文件>.scx.bak` 备份，保留可回滚能力。
- `SECURITY.md` 要求运行后检查配置与备份的权限与内容，避免把含凭据的备份提交。

### T6 MCP 客户端侧的提示注入与越权

**威胁**：模型被恶意内容影响，诱导调用工具读取敏感路径或超大负载。

**缓解**：
- 工具只暴露本地只读或限定范围内的操作，不提供任意路径读写。
- 参数做边界校验与长度上限；`Config::normalized()` 在入口收敛 NaN、负数与越界值。
- 工具描述被视为不可信来源的说明写入安全文档；宿主侧仍须取得用户同意（协议要求）。

### T7 供应链投毒

**威胁**：依赖被替换、CI 被越权、发布资产被篡改。

**缓解**：
- **零第三方 crate 依赖**（`Cargo.lock` 仅 `scx` 自身），消除依赖投毒面。
- CI 使用 `contents: read` 最小权限，第三方 action 固定 commit SHA。
- 发布资产附带 `SHA256SUMS.txt`，用户可校验完整性。
- **可复现构建**：两次独立目标目录构建产出相同 SHA-256，第三方可自行重建比对。
- 已识别缺口：发布资产尚未做密码学签名（`signed_releases` 未达标），
  当前完整性依赖 SHA-256 校验和与可复现构建，属**已知待补项**。

### T8 原生内核引入内存不安全

**威胁**：GPU 后端（`.cu` / `.metal`）绕过 Rust 的安全保证。

**缓解**：
- 内核只做线性代数，不含特征逻辑与用户可控的复杂分支。
- 内核源代码随仓库公开，参数与尺寸由 Rust 侧校验后传入。
- 不可用时自动回落 CPU 路径，CPU 路径为默认且全测试覆盖对象。

## 4. 安全设计原则的应用

| 原则 | 应用 |
| --- | --- |
| 最小权限 | CI `contents: read`；工具不提供任意路径读写 |
| 纵深防御 | 输入校验 + 边界规范化 + 路径白名单 + 失败即回退原文 |
| 失败安全 | 无信号、小输入、异常时回退原文并报告 `mode`，不静默降级 |
| 攻击面最小化 | 零依赖、无网络、无守护进程、无特权操作 |
| 完全中介 | 所有落盘经统一写入点，路径校验集中实现 |
| 不信任输入 | 所有解析返回 `Result`；参数在入口做边界收敛 |

## 5. 常见实现弱点与对抗

| 弱点类别（CWE 家族） | 本项目的对抗措施 |
| --- | --- |
| 缓冲区溢出 / 越界（CWE-119 系） | `forbid(unsafe_code)`；Rust 边界检查；无裸指针运算 |
| 不可信输入校验缺失（CWE-20） | 入口统一 `normalized()`；长度与取值域校验；非法输入拒绝而非猜测 |
| 路径穿越（CWE-22） | 受信前缀拼接 + 规范化校验 + 键白名单 |
| 资源耗尽（CWE-400） | 流式处理、`--max-mem` 分块、正则回溯上限 |
| 敏感信息暴露（CWE-200） | 尽力脱敏 + 明确的能力边界声明 + 不联网 |
| 供应链（CWE-1357） | 零依赖 + SHA-256 校验和 + 可复现构建 + 最小权限 CI |
| 并发竞态 | 并行路径为纯函数归约，共享状态仅限只读配置；并行测试干扰已单独识别并隔离 |

## 6. 超出范围

- 宿主机已被攻破（root 级）后的对抗
- 用户主动把秘密写入输入并在输出中分发
- 第三方 MCP 客户端自身的安全实现
- 模型层的行为安全（提示注入的语义判定由宿主负责）

## 7. 已知缺口（公开记录）

1. **发布签名**：`.github/workflows/release.yml` 已接入 cosign keyless 签名 +
   `SHA256SUMS.txt`，验证步骤见 [release-signing.md](release-signing.md)。
   该流程自下一次标签发布起生效；已发布的历史版本（v0.12.2 及更早）仅有 SHA-256 校验和。
2. **静态应用安全测试**：CI `security` 作业已在库目标上强制
   `unwrap_used` / `panic` / `todo` / `unimplemented` 为零，并禁止未文档化的 unsafe 块；
   但未接入 CodeQL 等跨过程数据流分析工具，`indexing_slicing` / `expect_used`
   作为记录项未列为阻断（当前分别约 860 处与 86 处，与既有实现风格相关）。
3. **无 fuzzing harness**：Rust 侧内存安全由类型系统与 `forbid(unsafe_code)` 保证，
   但解析器健壮性（畸形输入、超大负载）尚无持续随机测试。
4. **单一维护者**（bus factor = 1）：缓解措施见 [GOVERNANCE.md](../GOVERNANCE.md)。

上述缺口在补齐前不应对外宣称"已满足 silver 级"。
